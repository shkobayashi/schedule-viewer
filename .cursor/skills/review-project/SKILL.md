# review-project（schedule-viewer の全体レビュー）

ソースと文書を広くレビューし、根拠を確かめた指摘を `REVIEW.md` にまとめる。

## 着手前

1. 対象、対象外、成果物、指摘した箇所を直すかを計画で決める
2. [AGENTS.md](../../../AGENTS.md) に従い、ソースより先に [README.md](../../../README.md) と該当する `docs/` を読む
3. 文書は話の流れを確認できるよう一人で上から通読し、ソースは層ごとに分けて並行に調べる
4. 生成物、ロックファイル、ビルド出力を対象外にするときは、結果に明記する

## 自動チェック

計画の対象に応じて `npm run lint`、`npx tsc --noEmit`、`npm test`、`cargo clippy -- -D warnings`、`cargo test --locked`、`npm audit --omit=dev` を実行し、成否を結果へ記録する。

## 文書の観点

- 直訳調や不自然なカタカナ語には、文脈に合う言い換えを示す
- 用語が定義より先に現れないか、同じ概念に複数の語を使っていないかを確認する
- 見出しと段落を上から読み、前提、操作、結果が自然な順でつながるかを確認する
- 文書の目的から外れる実装の細部、重複、過剰な列挙を指摘する
- 版番号入りの例、今後の予定、既知の課題が現在の実装に追いついているかを確認する
- 文書とソースの食い違いに気づいたら、文書の指摘とは分けて記録する

## 実装の観点

- 不具合: 境界値、日付、非同期処理、履歴、保存、外部更新、入力エラーを確認する
- パフォーマンス: 描画中の再計算、二乗以上の処理、ポーリング、永続化の頻度を確認する
- セキュリティ: Tauri の権限と CSP、パス、HTML と SVG のエスケープ、入力サイズ、CI の権限を確認する
- アクセシビリティ: ラベル、フォーカス、キーボード操作、動的なエラーの通知を確認する
- 環境差: ブラウザ版とデスクトップ版で、検証、上限、エラー処理が意図せずずれていないかを確認する
- CI と Release: 変更パスの判定、生成物の差分、正本のバージョン、公開前の検査、権限を確認する
- 可読性: 大きすぎるファイルと関数、重複、責務、命名、コメント、テストの不足を確認する
- テスト仕様の一覧を実際のテスト名と照合し、手書き一覧の欠落や重複も確認する

## 検証

1. 指摘にはファイルと行、観点、重要度、内容、根拠または再現条件、提案を付ける
2. 重要度が高と中の指摘は該当コードを自分で読み直し、必要なら最小の再現確認をする
3. 推測だけの指摘を落とし、重複をまとめる。並行レビューの報告をそのまま成果物へ載せない

## 結果の書き方

`REVIEW.md` は、概要、自動チェック、優先して直す指摘、観点別の実装指摘、文書別の指摘、文書とソースの食い違い、テストの所見、スキルへ足した手順の順にする。

重要度は、高（データ消失、誤表示、セキュリティ上の穴）、中（条件付きの不具合、体感できる性能劣化）、低（可読性、保守性）、情報（任意の改善）とする。

## 完了条件

- 計画で決めた範囲を読み、自動チェックの結果と対象外を明記している
- 高と中の指摘を検証し、各指摘に場所、根拠、提案がある
- 計画と仕上がりがずれた箇所を直すときは、[AGENTS.md](../../../AGENTS.md) に従い、再発を防ぐ手順を該当スキルへ同じ変更で必ず足したかを結果に書く。足した節を書く。足さない判断だけを書いて完了にしない
- 成果物だけを求められた場合は、指摘したソースや文書を直していない
