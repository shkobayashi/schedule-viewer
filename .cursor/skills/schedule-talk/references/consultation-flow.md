# 相談の流れと部品の使い分け

schedule-talk で人と画面を見ながら相談するときの流れと、説明用の部品の選び方です。判断の手順はこの reference に置きます。MCP と read-screen のツール説明には、手順そのものは書きません。

## 相談の流れ

相談は、おおむね次の順に進みます。段を飛ばしたり、途中で戻ったりするのは場面次第です。

1. **聞く** — 何を決めたいか、どこを見ればよいかを押さえます。
2. **見せる** — 話題を絞る、場所を指す、比べる、のどれかで画面を合わせます。
3. **比べる** — やり方が複数あるときは、試しの計画で並べて聞きます。
4. **決める** — 人が名前や色で答えたら、選んだ案だけを採ります。
5. **入れる** — 選んだパターンを MCP の `apply_explanation_pattern` で未保存の計画へ一度に入れます。JSON を自分で書き直すのは、人がはっきり頼んだときだけです。
6. **閉じる** — 差分で中身を示し、保存するか戻すかは人が決めます。LLM は頼まれずに保存しません。`edit_plan` や `replace_schedule` で変えたあとの説明は、下の「計画を変えたあとの説明」に従います。

## 計画を変えたあとの説明

`edit_plan` または `replace_schedule` で計画を変え、成功して差分にタスクの変更が載ったあと、利用者が変わった場所をチャートで追えるようにします。

### 説明するか

- 変わった**タスクが2件以上**のときは、**必ず**説明します。
- **1件だけ**のときは、説明するか LLM の判断に任せます。
- 「計画は変わりませんでした。」のとき、または差分にタスクの変更が無いときは、この節の手順は不要です。

### 件数の数え方

- まず、ツールが返した差分テキストを読みます。`replace_schedule` で「差分が大きすぎるため、差分テキストは返せません。」のときは `schedule_diff` を読みます。画面とファイルの両方が動いているときは `baseline_diffs` も使います。
- FILE-07（[外部仕様の FILE-07](../../../../docs/external-spec.md)）と同じ規則で、**この更新**で変わったタスク id を重複なく数えます。追加・削除・フィールドの変更はいずれもタスク id ごとに数えます。見出し・マイルストン・繋がりだけの変更はタスクの件数に含めません。
- 差分が「比べるファイルがありません」だけのとき（パスが無い画面など）は、差分テキストでは数えられません。そのときは、今回の `edit_plan` の `ops` または `replace_schedule` で意図したタスク id を数えます。

### 説明の手順

1. 文書に残っている変えたタスク id を `explain_view` の `taskIds` で示します。`explain_view` は文書に無い id を拒否するので、**削除した id は渡しません**。削除はチャットで伝えます。場所を指しやすくする必要があるときは、`explain_overlay` の `summary` や `marks`（`kind: change` など）も使います。
2. 何をなぜ変えたかを短く伝えます。
3. 戻したいときは「やっぱり戻して」で `history` の取り消し（1 段）が使える旨を短く添えます。保存は人が頼むまでしません。

## 部品の使い分け

場面ごとの例です。決まり表ではありません。

### 説明のための絞り込みと折りたたみ（`explain_view`）

話題を狭めるときに使います。周りを隠しても判断できるときだけです。会議中に「関連するタスクだけ見せて」と頼まれたときなど。

- 会議中に「この帯だけ見せて」と頼まれたら、`milestoneGroupIds` で帯の行 id だけを残します。
- 「このマイルストンに関係するところだけ」と頼まれたら、`milestoneIds` と、必要なら `taskIds` を一緒に指定します。星に紐づくタスクは自動では残りません。

### 半透明と印と吹き出し（`explain_overlay`）

場所を指すときに使います。変更する場所と、判断を仰ぐ場所では `kind` を `change` と `ask` で分けます。クリティカルパスを見せて、と頼まれたときなど。

- 星の日付を動かすかを判断してほしいときは、その星 id に `ask` の印を付けます。日付列の印は、その日の星全部を明るくします。
- 帯の行全体を指すときは `milestoneGroupId` の印を使います。

### 試しの計画（`explain_overlay` の `patterns`）

やり方を複数並べて比べるときに使います。パターンごとに印の色を変え、`summary` でどれにするかを聞きます。

- 星の日付を前に倒す案と後ろに倒す案を並べるときは、各パターンの `milestoneChanges` で提案日付を変え、帯に点線のひし形を重ねます。

**例（パターン間で同じ変更）** — 赤と青の二案どちらでも、同じ星を同じ日付へ動かすだけのときは、星ごとにパターン色で二重に重ねず、共通の変更として `#ca8a04`（黄）の点線のひし形を一度だけ出します。`summary` に「黄色の点線は、どちらの案でも同じ変更です。」のように書きます。案ごとに違う変更だけ、パターンの `color` で描き分けます。

### 何も重ねない

一つの変更を進めてよいかだけを聞くときは、チャットと、その場所の吹き出しで足りることがあります。

### 変更の前に見せるか、後に見せるか

- **前に見せる** — 影響範囲が広い、複数案がある、人が全体像を見てから決めたいとき。絞り込み、印、試しの計画を組み合わせます。
- **後に見せる** — 小さな修正で、人が「ここだけ」と場所をはっきり指しているとき。1 件だけ変わった成功では、説明を省略してもよい（上の「計画を変えたあとの説明」）。2 件以上変わったときは必ず説明します。

## 途中でやめるとき

人が話題を変えた、別の操作を始めた、画面で「説明を消す」を押したときは、アプリが説明と試しの計画を捨てます。次のターンで読み取り、説明が残っているかを確かめます。消えていれば、出し直すか、そのまま進むかを場面で選びます。

別の話へ移る前に、LLM が `explain_overlay` の `translucent: false` や `explain_view` の `clear: true` で説明を消してよいことが多いです。パターンの中身はチャットに短く残し、同じ比較をまた見せられるようにします。

## 決まったあとに入れるとき

人が「A で」「青で」と答えたら、試しの計画が画面に残っているあいだに、次の順に進めます。

1. `apply_explanation_pattern` に、選んだパターンの `patternId` だけを渡します。`window` は付けません。先に `translucent: false` や `clear: true` で説明を消すと、試しの計画が無くなり拒否されます。
2. 成功したら、アプリが試しの計画と半透明を消します。返った差分テキストを読み、「計画を変えたあとの説明」に従って変わったタスクを示します。未保存のままにし、保存は人に任せます。

拒否されたとき（試しの計画が無い、パターン id が無い、試しの id が既存タスクと重なるなど）は、文書も試しの計画も変えません。理由を伝え、必要なら `explain_overlay` から出し直します。
