## PR599 のデバッグ教訓 {#pr599}

層をまたぐフォーカス不具合（[PR #599](https://github.com/shkobayashi/schedule-viewer/pull/599)）。Grok の計画と Composer の実装を何周かしたあと、Claude が直した、という経緯はある。これは履歴であり、ボットが Opus / Claude に作業を回す理由にはしない。

### 原因

- アサーションが読む状態（`focusedLabel`）を書く処理が、もう一つあった。
- 準備のときに記録した `focusedLabel` を、OS のフォーカスイベント処理（`os_focus_event`）が上書きしていた。
- 準備時点のログは、実行時の振る舞いの証明にならない。

### 残すやり方

1. アサーションが読む状態を書く処理をすべて洗い出し、順序を付ける。
2. ログは、準備のときではなく、判断する地点で取る。
3. 診断ログが一切出ないときは、修正を重ねる前に、既知の1行がそのチャネルに出ることを先に確かめる。
4. 当時の計測側の穴:
   - 子プロセスの出力は、プロセスが終了するまで `read_to_end` で読めなかった。
   - Tauri の権限が足りないと、何も言わずに失敗した。
5. 近い再発: PR618 でも、追加したログが CI に出ず、同じ穴に落ちかけた（`cargo test` が出力を隠した、と当時は見た。効果は当時未確認のまま）。2周目を調査だけの周にするなら、最初の作業は「既知の1行でログの出口が生きているかを確かめる」にする。
