# 計画メモ

## 目的

会議ログ・課題管理表などの入力情報をもとにLLMが立てたスケジュールを、表示・フィルタリング・編集・ズームイン/アウトできるツールを作る。

## 要件

- OS: Mac / Windows / Ubuntu 対応のGUIデスクトップアプリ
- 用途: LLM(Claude)が生成したスケジュールを表示・フィルタリング・編集・ズームイン/アウトする
- 方向性: WBS/ガントツールという見た目だが、制約やスケジュール計算の機能はすべてLLMとスキルに寄せ、アプリ自体には持たせない
- データ形式: JSON（`docs/schedule.schema.json`、`schemaVersion: 2`。終了日はその日を含む。v1 は読み込み時に v2 へ移行）
- 利用者: チーム内で配布・共有(自分専用ではない)

## 技術スタック(決定事項)

| 項目 | 選定 | 理由 |
|---|---|---|
| デスクトップシェル | Tauri | 軽量、Mac/Windows/Ubuntu対応、バックエンド(Rust)を薄く保てる |
| UI | React | エコシステム・人材の豊富さ、チームでの保守のしやすさ |
| タイムライン描画 | react-konva (Konva.js) | Canvas直描画でズーム時のレイアウト崩れがない。バーの直接ドラッグ&リサイズと相性が良い |
| LLM連携 | アプリに内蔵しない | スケジュールJSONはClaude(会話/スキル)側で生成し、アプリは表示・編集専用にして責務を最小化する |
| 配布 | Tauriバンドラ(dmg/msi/deb等) | チーム内配布 |

### 検討した代替案とその理由

- **PySide6(Qt) + QGraphicsView**: ライセンス・性能面では有力候補だったが、Qt自体の学習・実装コストへの懸念から見送り
- **Flet(Python+Flutter)**: Canvas上への自前描画がまだ発展途上のため見送り
- **pywebview**: Python資産をそのまま活かせるが、結局中身はHTML/CSSのレイアウトエンジンに頼るため、ズーム時のレイアウト崩れ懸念を解消できない
- **tldraw**: Canvas描画で操作感も良いが、商用利用(チーム配布含む)には有償ライセンス(または透かし表示)が必要なため不採用
- **React Flow**: MITライセンスで無料だが、本来ノード×エッジ(フローチャート)用のライブラリで、WBS/Ganttの「行×時間軸のバー」という構造にはやや無理がある
- → ライセンスフリーかつGanttの構造を素直に表現できる **Konva** を採用

## アーキテクチャ方針

- バックエンド(Rust)の責務は最小化する: ファイル読み書き・OSネイティブダイアログなどの薄い橋渡しのみ。計算ロジック・制約解決は一切持たない
- 「バックエンドはフロントでどこまでできるかで決める」方針のため、Phase 1はフロントのモックアップ・プロトタイプ作成を先行させた。Phase 1 は完了し、バックエンドに残るのはファイル読み書きだけである

## UI/UX方針

- タスクの編集は「直接操作型」を基本とする: タイムライン上でバーをドラッグして移動、端をドラッグしてリサイズ(期間変更)
- ダブルクリックでダイアログを開き、日付・担当者・ステータス・進捗などをフォームで編集する形も併用する
- フィルタリング: 担当者・ステータス・タスク名検索(軸は今後拡張の余地あり)
- ズーム: マウスホイール(Ctrl/Cmd+ホイール)でポインタ位置を基準にズーム。ズーム段階に応じて日表示/週表示/月表示のグリッド粒度を自動切替する
- ズームの実装は、CSS変換やDOMレイアウトに頼らず「1日あたりのピクセル数」を状態として持ち再描画する方式にする(パフォーマンスとレイアウト崩れ回避のため)

- GitHub単一リポジトリ（`CollabCentralOrganization/schedule-viewer`）
- 採用ディレクトリ構成（Phase 0 で反映済み）:

```

```

- **バージョン固定（Phase 0）**: Node.js 24、Rust 1.98.1（`rust-toolchain.toml` / `.nvmrc`）
- Tauri アプリ identifier: `com.collabcentral.schedule-viewer`
- 開発はVSCode + Claude Codeで実施
- DevContainerでNode.js + Rust(Tauri CLI)+ Linux向け依存(webkit2gtk等)を用意し、可搬性を確保する
  - **注意点**: DevContainerはコード編集・型チェック・ビルドまでは快適に行えるが、Tauriアプリの実際のウィンドウを起動しての動作確認はコンテナにディスプレイがないためホストOS側で行う必要がある(WSL2+WSLgやX11転送で多少緩和はできるが、基本はホスト実行が前提になる)

## ロードマップ

1. **Phase 0: 環境構築** — 完了。GitHubリポジトリ作成、DevContainer整備、Tauri+React雛形作成、Konva動作確認
2. **Phase 1: フロント作り込み** — 完了。`mockup/`のKonvaプロトタイプをReactコンポーネントに移植し、表示・フィルタ・編集・ズーム・系統・マイルストン・追加削除・配布用HTML書き出しまでを画面側で持つ。タスクの並び替えはしない
3. **Phase 2: JSONスキーマ確定** — 完了。`schemaVersion`・`title`・マイルストン・カテゴリ→グループ→タスク・`predecessors`・UUID ID。Ajv + 意味規則検証（`npm run check:schedule`）。別プロジェクト向け `.cursor/skills/write-schedule`（自己完結の検証スクリプト同梱）
4. **Phase 3: ファイルI/O実装** — 完了。JSON の開く・保存・別名保存（Tauri はネイティブダイアログ、ブラウザはファイル選択とダウンロード）。読み込み前に `validateSchedule`、未保存のまま開くときは確認
5. **Phase 4: 配布** — 各OS向けビルド・署名・チーム展開

## スケジュール JSON（Phase 2 確定）

- 正本: [schedule.schema.json](schedule.schema.json)
- ルート: `schemaVersion`（現状 2。終了日は含む）、`title`、`milestones[]`、`categories[]`
- タスク・マイルストンの `id` は UUID。カテゴリ・グループは名前が識別子（配列順＝画面の並び）
- 検証: `src/model/validateSchedule.ts`（アプリ）、`npm run check:schedule`（サンプル）、持ち出し用 `node .cursor/skills/write-schedule/scripts/validate-schedule.mjs <file>`
- LLM が JSON を書くとき: `.cursor/skills/write-schedule` を他リポジトリへコピーし、タスク管理側の情報が揃った状態で生成する

## 画面の現状

ツールバーの「開く」で検証済み JSON を読み込み、画面のデータを置き換える。未保存のまま開くとき、および Tauri でウィンドウを閉じるときは確認する。ブラウザでタブを閉じるときは、ブラウザ標準の確認になる。「保存」「別名保存」で同じ形式の JSON を書き出す。開いたファイルが保存前に外から変わっていたときは、上書き・別名保存・取り消しを選ぶ。見出し横の表示は、サンプル起動直後は「サンプルデータ」、編集後は「未保存」、保存済みはファイル名。⌘/Ctrl+Z で取り消し、⌘/Ctrl+Shift+Z または Ctrl+Y でやり直しができる。戻すのはカテゴリ・グループ・タスク・マイルストンの内容だけで、確定した編集（バー移動・期間変更・マイルストン移動・編集ダイアログの保存・追加・削除）を1操作1ステップとして最大100件まで覚える。フィルタ・折りたたみ・ズーム・スクロール・系統・選択は履歴に含めない。ファイルを開くと履歴は空になる。検索欄やダイアログ表示中はショートカットは文書を動かさない。「カテゴリ → グループ → タスク」の3段。カテゴリとグループは、見えている子の最早開始から最遅終了までのバーを持つ。バーの縦幅はタスクバーの半分で、子が途切れている期間は薄い色にする。左の三角で折りたため、畳んでも親バーは残る。配下に一致するタスクがないグループとカテゴリは一覧から省く。担当者は空（割り当てなし）を許容し、一覧はバッジ、バーは破線と上端の印で区別する。「割り当てなし」で絞れる。期限超過の未完了タスクは赤く、「完了以外」と「期限超過」で絞り込める。前後関係は各タスクの `predecessors` で持ち、ダイアログで先行・後続を編集する。線は先行と後続のタスク行が両方見えているときだけ描く。フィルタで消えたときも、どちらかが折りたたみで隠れているときも出さない。後続の開始が先行の終了より前の線は赤くし、「前後: 破綻のみ」でその両端だけを残せる。本日の縦線はイナズマ線にする。本日はアプリを動かしている日の日付で、日付が変わると更新する。期限超過の行では終了日まで左に折れ、着手済みで開始日が今日より後の行では開始日まで右に伸ばす。進捗率は見ない。タスクを選んでツールバーの「系統」をオンにすると、その先行を根まで、後続を末端まで辿ったタスクだけを残す。起点を通らない枝は含めない。ボタンには起点の名前を出し、もう一度押すと解除する。マイルストンはタスクではなく、名前と日付だけを持つ。日付ヘッダーと先頭行の間の帯にひし形と名前を置き、名前が重なるときは段を増やす。チャート全体へ線は引かない。ひし形のドラッグで日付を変え、ダブルクリックで名前と日付を編集する。各タスクは対応マイルストンを1つ持てる。未設定でもよい。設定したタスクだけ、終了日がそのマイルストンより後ならバーの越えた部分を赤くし、行に「超過」を出す。終了日がマイルストン当日なら超過にしない。ツールバーの「追加」でダイアログを開き、既存のカテゴリとグループ、タスク名、開始日、終了日を指定して、そのグループの末尾に足す。選択中タスクがあれば、そのカテゴリ・グループと日付を初期値にする。終了日はこの日を含む。開始日と同じ日なら1日のタスクになる。終了日が開始日より前なら追加しない。期間は1日未満にできず、編集ダイアログでもバーの端のドラッグでもそれより短くできない。新しいタスクは担当者なし・未着手・前後関係なし・マイルストン未設定で、IDは `crypto.randomUUID()`。追加した行が見えるよう、そのカテゴリとグループは展開し、系統表示は解除し、隠しているフィルタは外す。「削除」はタスクを選んでから押し、確認してから消す。消したIDは他タスクの先行から外し、前後のタスク同士はつながない。系統の起点を消したときは系統表示を解除する。空になったグループとカテゴリはデータに残し、追加ダイアログから選べる。タスクの並び替えはしない。並びはデータの順のままにする。「書き出し」は、絞り込み・折りたたみ・系統で見えている行を、スクロールで隠れている分も含め、今のズーム粒度のまま単一HTML（チャートはSVG）でダウンロードする。用紙へのページ割りはしない。生成はフロントで行う。左のカテゴリ名、グループ名、タスク名が幅に収まらないときは、その名前を横にドラッグして見切れた続きを読める。担当者と「超過」は動かない。
