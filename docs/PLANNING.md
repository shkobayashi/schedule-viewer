# 計画メモ

## 目的

会議ログ・課題管理表などの入力情報をもとにLLMが立てたスケジュールを、表示・フィルタリング・編集・ズームイン/アウトできるツールを作る。

## 要件

- OS: Mac / Windows / Ubuntu 対応のGUIデスクトップアプリ
- 用途: LLM(Claude)が生成したスケジュールを表示・フィルタリング・編集・ズームイン/アウトする
- 方向性: WBS/ガントツールという見た目だが、制約やスケジュール計算の機能はすべてLLMとスキルに寄せ、アプリ自体には持たせない
- データ形式: JSON（`docs/schedule.schema.json`、`schemaVersion: 6`。マイルストンは `milestoneGroups` と `groupId` で帯の行に分ける。カテゴリとグループは `id` を持ち、名前は表示である。担当は `assigneeId`、割り当てなしは `null`。タスクとマイルストンの `confidence` は `tentative` か `committed`。メンバー一覧は別 JSON。終了日はその日を含む。開けるのは schemaVersion 3〜6。v1 は終了日を移行したあと v2 として拒否する。詳細は [data-format.md](data-format.md)）
- 利用者: チーム内で配布・共有(自分専用ではない)

## 技術スタック(決定事項)

| 項目 | 選定 | 理由 |
|---|---|---|
| デスクトップシェル | Tauri | 軽量、Mac/Windows/Ubuntu対応、バックエンド(Rust)を薄く保てる |
| UI | React | エコシステム・人材の豊富さ、チームでの保守のしやすさ |
| タイムライン描画 | react-konva (Konva.js) | Canvas直描画でズーム時のレイアウト崩れがない。バーの直接ドラッグ&リサイズと相性が良い |
| LLM連携 | アプリに内蔵しない | スケジュールJSONはClaude(会話/スキル)側で生成し、アプリは表示・編集専用にして責務を最小化する |
| 配布 | Tauriバンドラ(dmg/msi/deb等) | チーム内配布 |

### 検討した代替案とその理由

- **PySide6(Qt) + QGraphicsView**: ライセンス・性能面では有力候補だったが、Qt自体の学習・実装コストへの懸念から見送り
- **Flet(Python+Flutter)**: Canvas上への自前描画がまだ発展途上のため見送り
- **pywebview**: Python資産をそのまま活かせるが、結局中身はHTML/CSSのレイアウトエンジンに頼るため、ズーム時のレイアウト崩れ懸念を解消できない
- **tldraw**: Canvas描画で操作感も良いが、商用利用(チーム配布含む)には有償ライセンス(または透かし表示)が必要なため不採用
- **React Flow**: MITライセンスで無料だが、本来ノード×エッジ(フローチャート)用のライブラリで、WBS/Ganttの「行×時間軸のバー」という構造にはやや無理がある
- → ライセンスフリーかつGanttの構造を素直に表現できる **Konva** を採用

## アーキテクチャ方針

- バックエンド(Rust)の責務は最小化する: ファイル読み書き・OSネイティブダイアログなどの薄い橋渡しのみ。計算ロジック・制約解決は一切持たない
- 「バックエンドはフロントでどこまでできるかで決める」方針のため、Phase 1はフロントのモックアップ・プロトタイプ作成を先行させた。Phase 1 は完了し、バックエンドに残るのはファイル読み書きだけである

## UI/UX方針

開発の初期に決めた方針で、経緯として残している。現在の操作は [外部仕様](external-spec.md) に書く。

- タスクの編集は「直接操作型」を基本とする: タイムライン上でバーをドラッグして移動、端をドラッグしてリサイズ(期間変更)
- ダブルクリックでダイアログを開き、日付・担当者・ステータス・進捗などをフォームで編集する形も併用する
- フィルタリング: 担当者・ステータス・タスク名検索(軸は今後拡張の余地あり)
- ズーム: マウスホイール(Ctrl/Cmd+ホイール)でポインタ位置を基準にズーム。ズーム段階に応じて日表示/週表示/月表示のグリッド粒度を自動切替する
- ズームの実装は、CSS変換やDOMレイアウトに頼らず「1日あたりのピクセル数」を状態として持ち再描画する方式にする(パフォーマンスとレイアウト崩れ回避のため)

## ロードマップ

1. **Phase 0: 環境構築** — 完了。GitHubリポジトリ作成、DevContainer整備、Tauri+React雛形作成、Konva動作確認
2. **Phase 1: フロント作り込み** — 完了。`mockup/`のKonvaプロトタイプをReactコンポーネントに移植し、表示・フィルタ・編集・ズーム・系統・マイルストン・追加削除・配布用HTML書き出しまでを画面側で持つ。タスクの並び替えはしない
3. **Phase 2: JSONスキーマ確定** — 完了。`schemaVersion`・`title`・マイルストン・カテゴリ→グループ→タスク・`predecessors`・UUID ID。Ajv + 意味規則検証（`npm run check:schedule`）。別プロジェクト向け `.cursor/skills/write-schedule`（自己完結の検証スクリプト同梱）
4. **Phase 3: ファイルI/O実装** — 完了。JSON の開く・保存・別名保存（Tauri はネイティブダイアログ、ブラウザはファイル選択とダウンロード）。読み込み前に `validateSchedule`、未保存のまま開くときは確認
5. **Phase 4: 配布** — GitHub Release で Ubuntu の deb と Apple Silicon の dmg を自動で作っている。Windows の安定版は Microsoft Store へ MSIX を提出し、更新は Windows が行う。ベータの Windows は Pre-release で自己署名の NSIS を出す。安定版の Release 本文にはその版の CHANGELOG を載せる。実機確認用の版は `release/X.Y.Z` から Pre-release として出し、本文は短い確認用の文だけである。Latest は安定版のうち、より大きいメジャーが無いときだけ付く。Ubuntu と macOS（GitHub Releases 版）のデスクトップ版は、設定でオンにしたときだけ、同じメジャー用の `updater-X` の `latest.json`（`linux-x86_64` と `darwin-aarch64`）から、より新しい安定版だけを署名付きで自動更新する。設定の「更新」で同梱の変更履歴を読める。操作マニュアルは `main` から https://shkobayashi.github.io/schedule-viewer/ で公開する。macOS の Release 用 dmg は ad-hoc 署名のみで、Developer ID と公証はしない

## v2.0

既存のプロジェクト管理ツールがしっくりこないことが多く、Excel の方眼紙でガントを作るプロジェクトは結構ある。方眼紙は自由度が高い一方で、構造化できず、git で管理できず、LLM で操作できない。誰にとってもベストなツールは作れない。v2.0 では自由度を残し、そのせいで面倒になる作業を LLM に任せる。

この自由度には、次の三つの制約を掛ける。

1. チームでの統一。
2. LLM の不確実さ。確実にすべきところは、自由度を捨てる。
3. 推論コスト。自由すぎると、推論コストは高くなる。

LLM に任せるのは、会議の内容からタスクの意味を決める作業である。日付の前後や、チームで揃える色は、推論で決めない。

要件にある「制約やスケジュール計算の機能はすべてLLMとスキルに寄せ、アプリ自体には持たせない」は、日付の前後に限って改める。その計算はアプリが行う。

### チームで揃えるステータス

ステータスは、メンバー一覧と同じく、スケジュール JSON とは別の JSON としてチームで共有する短い一覧を置く。各項目は `id`、表示名、色を持つ。タスクが持つのは `id` だけである。色は一覧から引く。ファイルごとに赤の意味は変わらない。

カテゴリとグループの名前と所属は、チームで揃えない。プロジェクトごとに違ってよい。

一覧に無い `id` は、中立の色で `id` だけを見せる。新しい色の意味は足さない。一覧を変える編集は、タスクを生成する推論とは分ける。

いまの `not-started`、`in-progress`、`done` の三値はやめる。この変更は v2.0 のファイル改訂で行う。

### アプリが描くもの

次はアプリが計算し、ステータスの塗りとは別に描く。推論では決めない。

- 終了日が今日より前か。超過でバー全体の色は置き換えない
- 後続が先行の終了より前に始まるか
- 今日がバーのどこにあるか。イナズマ線はこれを描く
- 非稼働日はどこか

進捗率はタスクの値であり、アプリはその割合をバーの中に描く。割合からステータスや色は決めない。

ファイルに条件文は書かない。「線を超えたらこの色」という式は持たない。進捗の線を超えた事実の表示はアプリが行う。タスクをどのステータスにするかは、一覧の中から LLM が選ぶ。

日付の形、終了が開始以降であること、`id` の参照、循環の禁止は、スキーマで閉じたままにする。v2.0 で加えるのは、ステータスが一覧に存在することである。

### 推論の範囲

タスクの件数に比例して決定が増える自由は持たない。`write-schedule` は、使えるステータスの `id` を固定の表として持つ。生成のたびに一覧を設計しない。

### タスクの自由度

残すものは、カテゴリとグループの名前と所属、日付、前後関係、進捗、ノート、タグである。階層は、カテゴリ、グループ、タスクの三段のままである。タグとノートは自由記述のままにする。色は決めない。絞り込みの軸にもしない。

持たないものは、タスクごとの色、ステータスの自由文字列、ファイルに書く条件、階層の段数の可変である。

## 決定（MCP を使えないときの画面の状態）

- コマンドは `--screen` とツール名、または読み取り 5 つに `--window` と内部ラベル。ツール名に `open_windows` を含む。`open_windows` と `replace_schedule` に `--window` は付けない。`replace_schedule` は標準入力にスケジュール JSON 全体
- スキル名は `read-screen`。同梱テンプレートの実行ファイルの呼び方を、置くときにこのパソコンのものへ書き込む。Windows で Local AppData 配下のときは `"$LOCALAPPDATA/"` から続く1行にし、それ以外は絶対パスを引数と別の行に書く
- 置き先はユーザー全体（`~/.cursor/skills/read-screen/` と `~/.claude/skills/read-screen/`）だけ。指定フォルダは出さない
- 設定の「画面の状態を渡す」に、mcp.json 登録とスキル置きを並べる。どちらか一方を終えても、もう一方は終わらない

## 決定（JSON 作成スキルの配置）

- `write-schedule`、`write-members`、`write-calendar` は配布ビルドに同梱する。利用者が置く操作はデスクトップ版の設定から行う
- deb や NSIS などのインストーラーは、ホームやプロジェクトへスキルをコピーしない。初回起動でも勝手に書かない

## 既知の課題

- `mockup/` はアプリから参照しない。プレビュー環境で Konva.js が読み込めない問題は、対応しない。
