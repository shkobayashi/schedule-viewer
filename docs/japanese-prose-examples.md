## 禁止と比喩（J3）

**使わない（比喩・別物指し）:**

- 「同じ入口に載る」「もう一周増える」
- 「正本」「経路」「入り口」「入口」を、画面・文書に無い意味で使う（`operation-entries.md` の「操作の入口」など**資料の名前**はそのまま可）

**使わない（文の切り方）:**

- 「〜です。〜です。」だけを続ける（関係は「なので」「ただし」）

### schedule-viewer 向け 悪い例 → 良い例（相談・設計）

**悪い例（出力禁止）:** 統合スキルの目次は同じ入口に載りません。もう一周増えます。正本が分かれます。経路が違います。入り口も違います。同梱してもよいです。別スキルでもよいです。

**良い例（型）:** 統合スキルを作り、SKILL.md を目次にしてノウハウを reference に置く案の是非、という相談ですね。統合スキルは作らず、色で指す手順は reference にして read-screen に同梱するのがいい。**理由1:** 統合スキルが先に読まれる保証がない。スキルは説明文が当たったものが開かれる。なので別のスキルが先に開くと、目次は読まれない。**変える場所:** 色で指す手順を reference に書き、read-screen に、見た目で指されたらその reference を読む、と一行足す。**残る選択肢:** 見た目で指したときだけ開く別スキルもある。開く条件は合うが、配置の仕組みの追加が要る。

（consult.mdc の「直し方の例」と同一。削除せずここを正本に移した。）

### AGENTS / 実装向け 悪い例 → 良い例（J3・資料名）

| 悪い例（出力禁止） | 良い例 |
| --- | --- |
| 絵が乗れば、画面の中身は渡っています。 | チャートの画像も含めて渡します。 |
| 読み取りで意図して残している穴が効いてきます。 | 読み取りでは渡していない、確定前の文字やドラッグ中の日付が、書き込みでは問題になります。 |
| プログラムの計測をそこへ混ぜない、という線もそのままでよいです。 | プログラム内部の計測値は、これまでどおり渡しません。 |
| 効き方で分けると、見方を変える操作は、絞り込み、折りたたみ… | 書き込みは、次の三つに分けます。（絞り込み… / 計画の中身… / ファイルに残す…） |

（旧 japanese-prose「直し方の例」から移動。**削除 0**。）

## 相談の型（consult 用・J1 J2）

`/consult` 時は [consult.mdc](../.cursor/rules/consult.mdc) の**返答の順**が優先する。

1. 依頼を一文で復唱（「〜という相談ですね」可）。目的は〜である、で始めない。
2. 次の一文で**推す結論を一つ**（二択で終わらない）。
3. **理由1:** 見出し — 本文は短く、「なので」「ただし」で結論とつなぐ。
4. **変える場所** / **残る選択肢**

例とたとえ: 利用者が明示したときだけ（J4）。上の統合スキル見本は**ルール用**で、毎回の出力に使わない。

## どの文章でも（J1 のチェックリスト）

- 1文で言えることは1文。回りくどく書かない。
- 段落は一つのこと。次は次の段落。
- 処理・仕組みは**目的を先**に。手順の羅列で説明を代用しない。
- 難しい処理は狙いを一文でまとめてから詳細。短い名詞一語のまとめにしない。
- 「前提を〜にするなら」を繰り返さない。必要なら「もし〜を優先するなら」。
- 比喩は1–2回まで。続けて重ねない。
- 資料の言葉を使うときは、**どの文書のどの表・節**か書く（チャットでは同じ箇所を見ているとは限らない）。

---

## チャット（J2）

- です・ますの自然な話し言葉。翻訳調・論文調・仕様書調にしない。
- 相談モードでは復唱を省かない（consult.mdc）。

---

## 文書・Issue・PR・コミット（J5）

文体は編集先ファイルに合わせる。チャットだけ仕様書調にしない。

## write-* スキルとの関係

JSON 作成スキル（write-schedule 等）の日本語は、**不足を推測で埋めない**など [agents-pitfall-examples.md](agents-pitfall-examples.md) 原則 2 と同型。スキル内の検証メッセージは各 SKILL が正本。アプリ実装手順の日本語は implement-change が正本。
