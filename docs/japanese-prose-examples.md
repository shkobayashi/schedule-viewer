## 禁止と比喩（J3）

**使わない（比喩・別物指し）:**

- 「同じ入口に載る」「もう一周増える」
- 「正本」「経路」「入り口」「入口」を、画面・文書に無い意味で使う（`operation-entries.md` の「操作の入口」など**資料の名前**はそのまま可）

**使わない（文の切り方）:**

- 「〜です。〜です。」だけを続ける（関係は「なので」「ただし」）

### 相談・設計向け（統合スキルの話題）

**悪い例（出力禁止）:** 統合スキルの目次は同じ入口に載りません。もう一周増えます。正本が分かれます。経路が違います。入り口も違います。同梱してもよいです。別スキルでもよいです。

**良い例（型・相談モードでは段落を分ける）:** 統合スキルを作り、SKILL.md を目次にしてノウハウを reference に置く案の是非、という相談ですね。統合スキルは作らず、色で指す手順は reference にして read-screen に同梱するのがいいと思います。

**理由1:** 先に読まれる保証がない。スキルは説明文が当たったものだけが開かれるので、別のスキルが先に開くと目次は読まれません。

**変える場所:** 色で指す手順を reference に書き、read-screen には「見た目で指されたらその reference を読む」と一行足します。

**残る選択肢:** 見た目で指したときだけ開く別スキルもあります。開く条件は合いますが、配置の仕組みを足す必要があります。

（旧 japanese-prose「直し方の例」と consult の型見本。別の話題では、同じ型で、その話題の名前を使う。）

### 実装向けの言い換え（J3・資料名）

| 避ける言い方（出力禁止） | 代わりの言い方 |
| --- | --- |
| 絵が乗れば、画面の中身は渡っています。 | チャートの画像も含めて渡します。 |
| 読み取りで意図して残している穴が効いてきます。 | 読み取りでは渡していない、確定前の文字やドラッグ中の日付が、書き込みでは問題になります。 |
| プログラムの計測をそこへ混ぜない、という線もそのままでよいです。 | プログラム内部の計測値は、これまでどおり渡しません。 |
| 効き方で分けると、見方を変える操作は、絞り込み、折りたたみ… | 書き込みは、次の三つに分けます。（絞り込み… / 計画の中身… / ファイルに残す…） |

## 作業報告のチャット（J1 J2 J3）

以下の悪い例は**架空の例文**である。件数やコミット名は、実際のリポジトリの値として書かない。

### 3.1 結論より先に、ファイル名と件数を並べる（J1）

**悪い例（出力禁止）:** `docs/japanese-prose-examples.md` と `japanese-prose.mdc` を更新しました。テストは 1234 件、lint の警告は 56 件です。レビュー指摘は 4 点で、コミット `abc1234` で直しています。

**良い例:** 日本語のルールは、毎回読むファイルには短い原則だけを残し、具体的な良し悪しの例は別の文書に移しました。テストと警告の件数は、これまでと同じで問題ありません。

### 3.2 表と太字ラベルの報告書（J2）

**悪い例（出力禁止）:**

**変更点**

| ファイル | 内容 |
| --- | --- |
| `japanese-prose.mdc` | J1–J5 を追加 |

**結果:** 黙って消した条文はありません。

**良い例:** 日本語のルールを、短い原則と、参照用の例に分けました。以前から書いてあった注意は、黙って消してはいません。

### 3.3 「項目: 値」の断片と英語見出し（J2）

**悪い例（出力禁止）:** 対象: チャット。原則: J1–J5。ガード: 毎回読み込み。状態: ある。Final principles は 8 件です。

**良い例:** チャットの返事にも、この原則が効くようにしました。原則は 8 つです。前は「あったらいい」だった仕組みのうち、いくつかは今回から実際に効きます。

### 3.4 造語や番号を、説明なしに使う（J3）

**悪い例（出力禁止）:** P-AG-03 と J3 に従い、正本と入口の束を examples に移しました。

**良い例:** クラウドのエージェントが、すでに取り込んだ枝へ続きを載せないよう、開発の手順書に一文足しました。画面や文書に無い「正本」や「入口」といった言い方の直しは、例の文書に置いてあります。

### 3.5 決まった進め方を、結論で打ち消す

**悪い例（出力禁止）:** 指摘は実装と同じコミットに含めました。別コミットは不要です。

**良い例:** レビューで直した内容は、いつものとおり別のコミットにしました。

### 3.6 ほぼ一通りなのに、質問で止める（J1）

**悪い例（出力禁止）:** 原則を短くして例は別ファイルに分ける案と、今の長いルールのままにする案があります。どちらで進めますか。

**良い例:** 短い原則と、参照用の例に分けるのがよいと思います。毎回のチャットで長い規則を読ませずに済むからです。今の長いルールのままにする考え方もありますが、今は分け方を推します。

### 3.7 仕様書調・英語ブログ調の日本語（J2）

**悪い例（出力禁止）:** 本変更は、日本語出力における可読性の向上を目的として、原則の再構成を実施したものである。

**良い例:** 読みにくさの原因ごとに、短い原則へまとめ直しました。

### 3.8 相談の良い例（一段落に詰めない）

**良い例（型）:** 統合スキルを作り、SKILL.md を目次にしてノウハウを reference に置く案の是非、という相談ですね。統合スキルは作らず、色で指す手順は reference にして read-screen に同梱するのがいいと思います。

## 相談の型（consult 用・J1 J2）

`/consult` 時は [session.md](../.cursor/skills/consult/references/session.md) の**返答の順**が優先する。**通常の作業報告では、この見出し型や表で報告書を組まない**（J2）。

1. 依頼を一文で復唱（「〜という相談ですね」可）。目的は〜である、で始めない。
2. 次の一文で**推す結論を一つ**（二択で終わらない）。
3. **理由1:** 見出し — 本文は短く、「なので」「ただし」で結論とつなぐ。見出しごとに段落を分ける。
4. **変える場所** / **残る選択肢**

たとえ: 利用者が明示したときだけ（J4）。上の統合スキル見本は**ルール用**で、毎回の出力に使わない。

## どの文章でも（J1 のチェックリスト）

文は、その文で伝えたいことに沿った表現にする。案でも、案以外の地の文でも同じである。

- 1文で言えることは1文。回りくどく書かない。
- 段落は一つのこと。次は次の段落。
- 処理・仕組みは**目的を先**に。手順の羅列で説明を代用しない。
- 難しい処理は狙いを一文でまとめてから詳細。まとめの一文も、短い名詞にせず、誰が何をするかで書く。
- 読み手が「これは何を言っているのか」と止まりそうな言い回しは使わない。
- 「これが表しているのは〜」とは書かない。「つまり」「要するに」「ここで見ているのは」のように書く。
- 「前提を〜にするなら」を繰り返さない。必要なら「もし〜を優先するなら」。
- 地の文では、同じ構文を3回以上続けない。同じ内容を別の角度から言い直すときは、言い回しも変える。箇条書きや表の項目は、形を揃えてよい。
- 比喩は1–2回まで。続けて重ねない。
- 資料の言葉を使うときは、**どの文書のどの表・節**か書く（チャットでは同じ箇所を見ているとは限らない）。

## チャット（J2）

- です・ますの自然な話し言葉。翻訳調・論文調・仕様書調にしない。
- レポートや仕様書の口調にせず、会話として書く。
- **通常の作業報告では、依頼の復唱から始める必要はない。** 相談モードでは復唱を省かない（[session.md](../.cursor/skills/consult/references/session.md) の「返答の順」）。相談の見出し（理由1、変える場所など）はレポート調には数えないが、**相談のときだけ**使う。
- 利用者が「分からない」と言ったら、同じ説明を繰り返さず、別の言い方で言い直す。

## write-* スキルとの関係

JSON 作成スキル（write-schedule 等）の日本語は、**不足を推測で埋めない**など [agents-pitfall-examples.md](agents-pitfall-examples.md) 原則 2 と同型。スキル内の検証メッセージは各 write-* SKILL。アプリ実装手順の日本語は implement-change。
